# WEMOVE 团队协作与版本规范

本规范适用于 `wemove-product-portal`。目标是让 7 位成员可以并行开发，代码可追溯、可审核、可安全整合。

## 1. 基本原则

- 不允许任何成员直接向 `main` 推送代码；所有修改必须通过 Pull Request（PR）合并。
- 一个功能由对应负责人完成前台页面、接口、数据表迁移、后台管理页和必要测试，避免按“前端/后端”拆分造成反复交接。
- 每次提交只解决一个明确问题；不要在同一个 PR 中混入格式化、重构和无关功能。
- 合并前以仓库实际脚本为准完成构建、测试或手动验证；验证结论写入 PR。

## 2. 模块归属

| 成员 | 模块代号 | 数据与代码归属 |
| --- | --- | --- |
| 1 号 | `platform` | 登录、角色权限、公共布局、项目配置、数据库迁移约定、CI 与集成 |
| 2 号 | `content` | 首页、品牌/内容页面、内容 CMS |
| 3 号 | `product` | 分类、商品、规格参数、商品列表/详情/对比、产品管理 |
| 4 号 | `support` | FAQ、下载资料、说明书、联系表单、询盘处理 |
| 5 号 | `dealer` | 经销商申请、审核、公司资料、简化经销商工作台 |
| 6 号 | `account` | 个人资料、收藏、地址、我的咨询记录 |
| 7 号 | `quality` | 搜索、站点地图、SEO、埋点、测试用例、回归与验收 |

跨模块需求必须先在 Issue 或 PR 讨论区说明接口，再由数据所属模块负责人实现接口。禁止直接修改其他模块的数据表、核心业务逻辑或接口语义。

## 3. 分支命名

先更新本地 `main`，再从 `main` 创建功能分支。分支格式：

```text
<类型>/<模块代号>-<简短英文描述>
```

允许的类型：

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| `feat` | 新功能 | `feat/product-product-detail` |
| `fix` | 缺陷修复 | `fix/account-favorite-state` |
| `docs` | 文档变更 | `docs/quality-test-cases` |
| `test` | 测试补充或调整 | `test/support-contact-form` |
| `refactor` | 不改变功能的代码整理 | `refactor/platform-auth-middleware` |
| `chore` | 工程配置、依赖或脚本 | `chore/platform-eslint-config` |

一个分支只对应一个功能点或一个缺陷。功能完成、PR 合并后删除远端分支；不要复用已合并分支继续开发。

## 4. 提交信息规范

提交信息格式：

```text
<type>(<scope>): <简短说明>
```

`type` 与分支类型一致；`scope` 使用模块代号。说明使用动词开头，不加句号，控制在一行内。

```text
feat(product): 新增商品详情规格展示
fix(support): 修复联系表单必填校验
docs(quality): 补充经销商申请测试用例
chore(platform): 配置开发环境变量示例
```

以下情况必须拆分提交：

- 新功能与无关重构；
- 数据库迁移与无关页面修改；
- 修复缺陷与批量格式化；
- 多个没有因果关系的功能。

## 5. 上传代码流程

```bash
# 1. 同步主分支（开发前执行）
git switch main
git pull origin main

# 2. 创建自己的功能分支
git switch -c feat/product-product-detail

# 3. 开发并检查变更
git status
git diff

# 4. 暂存并提交
git add <具体文件路径>
git commit -m "feat(product): 新增商品详情规格展示"

# 5. 推送分支
git push -u origin feat/product-product-detail
```

推送后在 GitHub 创建 PR，目标分支选择 `main`。不要执行 `git push origin main`，不要使用强制推送覆盖他人代码。

## 6. PR 标题与内容

PR 标题沿用提交格式，例如：

```text
feat(product): 新增商品详情规格展示
```

PR 描述必须包含：

```markdown
## 改动内容
- [ ] 页面
- [ ] 接口
- [ ] 数据库迁移
- [ ] 测试/文档

## 验证方式
- 执行的命令或手动验证步骤：
- 验证结果：

## 影响范围
- 涉及模块：
- 是否新增环境变量、迁移或接口：是 / 否

## 截图（如有页面改动）
```

发起 PR 前确认：

- [ ] 分支基于最新 `main`；
- [ ] 不包含密钥、账号、`.env` 或本地缓存文件；
- [ ] 没有无关文件或大范围格式化；
- [ ] 自测通过，且验证方式已写明；
- [ ] 涉及接口时，参数、返回值和错误情况已经说明；
- [ ] 涉及数据库时，迁移可重复执行且可在空数据库初始化。

## 7. 审核、合并与冲突

- 所有人可以提交 PR；由仓库管理员 `@chenyi-c` 审核并合并 `main`。
- PR 被要求修改后，继续向原分支提交，不要重复开新的 PR。
- 出现冲突时，由该 PR 作者解决；先同步最新 `main`，在本地解决并重新验证后推送。
- 解决冲突时不得删除或改写不属于自己的模块；无法判断时在 PR 中 @ 对应负责人。
- 任何影响公共接口、路由、用户表或工程配置的变更，须由 1 号成员与相关模块负责人共同确认。

## 8. 版本号与发布规范

采用语义化版本：`MAJOR.MINOR.PATCH`，课程项目从 `v0.1.0` 开始。

| 版本变化 | 含义 | 示例 |
| --- | --- | --- |
| `PATCH` | 修复缺陷、不改变既有功能 | `v0.1.0` → `v0.1.1` |
| `MINOR` | 完成一个可演示的新模块或功能集 | `v0.1.1` → `v0.2.0` |
| `MAJOR` | 不兼容架构或接口调整，通常课程项目中慎用 | `v0.2.0` → `v1.0.0` |

建议里程碑：

- `v0.1.0`：项目骨架、登录权限、基础页面可运行；
- `v0.2.0`：产品与内容主流程完成；
- `v0.3.0`：支持中心、用户中心、经销商申请完成；
- `v0.4.0`：搜索、SEO、测试与演示数据完成；
- `v1.0.0`：课程答辩交付版，冻结功能，只修复阻塞性问题。

每次发布由 1 号成员创建 GitHub Release，并在 Release Notes 写清：新增功能、修复问题、已知限制、数据库迁移或环境变量变化。

## 9. 禁止上传的内容

- `.env`、真实密钥、Token、数据库密码、第三方账号；
- `node_modules`、构建产物、IDE 本地配置、日志、缓存；
- 未授权的图片、付费模板、第三方源码；
- 真实用户隐私数据或生产数据库导出文件。

需要提交环境变量时，只提交 `.env.example`，变量值使用占位符。

## 10. 课程一期范围边界

本期重点交付“内容展示 + 产品管理 + 支持资料 + 用户/经销商申请 + 后台管理”的可演示闭环。在线支付、退款、物流、实时库存、ERP/WMS/CRM、多币种、多语言与复杂经销商报价属于后续规划，未经全组确认不得自行扩展进入本期。
