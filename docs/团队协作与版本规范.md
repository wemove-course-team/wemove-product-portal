# WEMOVE 团队协作与版本规范

本规范适用于 `wemove-product-portal`。目标是让 7 位成员可以并行开发，代码可追溯、可审核、可安全整合。

## 1. 基本原则

- 不允许任何成员直接向 `main` 推送代码；所有修改必须通过 Pull Request（PR）合并。
- 一个功能由对应负责人完成前台页面、接口、数据表迁移、后台管理页和必要测试，避免按“前端/后端”拆分造成反复交接。
- 每次提交只解决一个明确问题；不要在同一个 PR 中混入格式化、重构和无关功能。
- 合并前以仓库实际脚本为准完成构建、测试或手动验证；验证结论写入 PR。
- 最终集成、回归测试和课程验收由全组共同完成，不设为任何一个人的独占模块。

## 2. 模块归属

| 成员 | 模块代号 | 数据与代码归属 |
| --- | --- | --- |
| 1 号 | `platform` | 登录、角色权限、公共布局、项目配置、数据库迁移约定、CI 环境 |
| 2 号 | `content` | 首页、品牌/内容页面、内容 CMS、内容页 SEO |
| 3 号 | `product` | 分类、商品、规格参数、商品列表/详情/对比、产品管理、商品搜索 |
| 4 号 | `support` | FAQ、下载资料、说明书、联系表单、询盘处理 |
| 5 号 | `dealer` | 经销商申请、审核、公司资料、简化经销商工作台 |
| 6 号 | `account` | 个人资料、收藏、地址、我的咨询记录 |
| 7 号 | `operation` | 运营后台首页、数据看板、系统公告、站内通知、操作日志、全站基础设置 |

业务后台的“商品管理、内容管理、资料管理、经销商审核、用户资料”等页面仍由各业务模块负责人维护；7 号只负责通用运营工作台与只读数据汇总，不接管其他模块的 CRUD。跨模块需求必须先在 Issue 或 PR 讨论区说明接口，再由数据所属模块负责人实现接口。禁止直接修改其他模块的数据表、核心业务逻辑或接口语义。

## 3. 代码目录规范

基础前端上传后作为 `v0.1.0` 基线。已有页面可以逐步迁移，但后续新增功能必须按以下目录边界放置；不要把所有页面、组件和接口集中堆在顶层目录。

```text
src/
├─ app/                 # 1 号：应用入口、路由、全局 Provider
├─ layouts/             # 1 号：前台与后台公共布局
├─ shared/              # 公共组件、请求封装、工具函数、全局类型
├─ modules/
│  ├─ platform/         # 1 号：登录与权限
│  ├─ content/          # 2 号：首页与内容 CMS
│  ├─ product/          # 3 号：商品、分类与搜索
│  ├─ support/          # 4 号：资料、FAQ 与咨询
│  ├─ dealer/           # 5 号：经销商
│  ├─ account/          # 6 号：个人中心
│  └─ operation/        # 7 号：运营后台
├─ assets/              # 公共图片、字体、图标
└─ styles/              # 全局主题与基础样式
```

每个业务模块内部采用同一结构；不存在的目录不必为了整齐而创建：

```text
src/modules/product/
├─ pages/               # 路由页面
├─ components/          # 仅本模块复用的组件
├─ api/                 # 本模块接口请求
├─ types/               # 本模块数据类型
├─ hooks/               # 本模块 Hook
└─ store/               # 本模块状态；没有则不建
```

后端建立后也按相同模块代号划分，例如 `server/modules/product/`；数据表迁移、接口处理和业务服务均由对应模块负责人维护。

- `app`、`layouts`、`shared`、`styles`、主路由属于公共目录。修改它们必须单独开 PR，并在 PR 中说明影响范围。
- 业务成员只直接修改自己 `src/modules/<模块代号>/` 下的文件；跨模块功能通过接口或公共组件对接，不能直接引用对方内部组件。
- 仅在两个及以上模块稳定复用的组件才可移入 `shared/components`；移入前须征得 1 号和使用方同意。
- 测试文件紧邻被测代码，例如 `src/modules/product/pages/ProductDetailPage.test.tsx`。
- 不提交真实密钥、`.env`、构建产物、依赖目录或本地缓存；环境变量只提交 `.env.example`。

## 4. 分支命名

先更新本地 `main`，再从 `main` 创建功能分支。分支格式：

```text
<模块代号>-<姓名拼音>-<简短英文描述>
```

例如：

```text
product-zhangsan-product-detail
support-lisi-contact-form-validation
operation-wangwu-dashboard
```

一个分支只对应一个功能点或一个缺陷。功能完成、PR 合并后删除远端分支；不要复用已合并分支继续开发。

## 5. 提交信息规范

提交信息格式：

```text
<模块代号>-<姓名拼音>: <简短中文介绍>
```

模块代号必须与模块归属表一致；姓名拼音使用固定写法；说明使用动词开头，不加句号，控制在一行内。

```text
product-zhangsan: 新增商品详情规格展示
support-lisi: 修复联系表单必填校验
operation-wangwu: 新增运营数据看板
platform-chenyi: 配置开发环境变量示例
```

以下情况必须拆分提交：

- 新功能与无关重构；
- 数据库迁移与无关页面修改；
- 修复缺陷与批量格式化；
- 多个没有因果关系的功能。

## 6. 上传代码流程

```bash
# 1. 同步主分支（开发前执行）
git switch main
git pull origin main

# 2. 创建自己的功能分支
git switch -c product-zhangsan-product-detail

# 3. 开发并检查变更
git status
git diff

# 4. 暂存并提交
git add <具体文件路径>
git commit -m "product-zhangsan: 新增商品详情规格展示"

# 5. 推送分支
git push -u origin product-zhangsan-product-detail
```

推送后在 GitHub 创建 PR，目标分支选择 `main`。不要执行 `git push origin main`，不要使用强制推送覆盖他人代码。

## 7. PR 标题与内容

PR 标题沿用提交格式，例如：

```text
product-zhangsan: 新增商品详情规格展示
```

PR 描述必须包含：

```markdown
## 改动内容
- [ ] 页面
- [ ] 接口
- [ ] 数据库迁移
- [ ] 测试/文档

## 验证方式
- 执行的命令或手动验证步骤：
- 验证结果：

## 影响范围
- 涉及模块：
- 是否新增环境变量、迁移或接口：是 / 否

## 截图（如有页面改动）
```

发起 PR 前确认：

- [ ] 分支基于最新 `main`；
- [ ] 不包含密钥、账号、`.env` 或本地缓存文件；
- [ ] 没有无关文件或大范围格式化；
- [ ] 自测通过，且验证方式已写明；
- [ ] 涉及接口时，参数、返回值和错误情况已经说明；
- [ ] 涉及数据库时，迁移可重复执行且可在空数据库初始化。

## 8. 审核、合并与冲突

- 所有人可以提交 PR；由仓库管理员 `@chenyi-c` 审核并合并 `main`。
- PR 被要求修改后，继续向原分支提交，不要重复开新的 PR。
- 出现冲突时，由该 PR 作者解决；先同步最新 `main`，在本地解决并重新验证后推送。
- 解决冲突时不得删除或改写不属于自己的模块；无法判断时在 PR 中 @ 对应负责人。
- 任何影响公共接口、路由、用户表或工程配置的变更，须由 1 号成员与相关模块负责人共同确认。
- 课程答辩前的集成、回归和验收由全员共同完成；每个人负责验证自己模块的主流程与跨模块入口。

## 9. 版本号与发布规范

采用语义化版本：`MAJOR.MINOR.PATCH`，课程项目从 `v0.1.0` 开始。

| 版本变化 | 含义 | 示例 |
| --- | --- | --- |
| `PATCH` | 修复缺陷、不改变既有功能 | `v0.1.0` → `v0.1.1` |
| `MINOR` | 完成一个可演示的新模块或功能集 | `v0.1.1` → `v0.2.0` |
| `MAJOR` | 不兼容架构或接口调整，通常课程项目中慎用 | `v0.2.0` → `v1.0.0` |

建议里程碑：

- `v0.1.0`：项目骨架、登录权限、基础页面可运行；
- `v0.2.0`：产品与内容主流程完成；
- `v0.3.0`：支持中心、用户中心、经销商申请完成；
- `v0.4.0`：运营后台、搜索、SEO、演示数据与全员回归完成；
- `v1.0.0`：课程答辩交付版，冻结功能，只修复阻塞性问题。

每次发布由 1 号成员创建 GitHub Release，并在 Release Notes 写清：新增功能、修复问题、已知限制、数据库迁移或环境变量变化。

## 10. 禁止上传的内容

- `.env`、真实密钥、Token、数据库密码、第三方账号；
- `node_modules`、构建产物、IDE 本地配置、日志、缓存；
- 未授权的图片、付费模板、第三方源码；
- 真实用户隐私数据或生产数据库导出文件。

需要提交环境变量时，只提交 `.env.example`，变量值使用占位符。

## 11. 课程一期范围边界

本期重点交付“内容展示 + 产品管理 + 支持资料 + 用户/经销商申请 + 后台管理”的可演示闭环。在线支付、退款、物流、实时库存、ERP/WMS/CRM、多币种、多语言与复杂经销商报价属于后续规划，未经全组确认不得自行扩展进入本期。
