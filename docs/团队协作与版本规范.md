# WEMOVE 团队协作与版本规范

本规范适用于 `wemove-product-portal`。当前已合并的 Vue 3 前端、图片资源和数据库初始化脚本是全组后续开发的共同基线；后续工作应在该基础上迭代，不另起一套前端目录或重复搭建工程。

## 1. 当前基线与项目边界

- 当前前端位于 `frontend/`，采用 Vue 3、Vite、Vue Router、Pinia 与 Element Plus。
- 当前登录、角色、商品、经销商审核、购物车和订单均使用 Mock 数据与浏览器 `localStorage` 演示；它们不是后端鉴权、真实支付、真实物流或真实订单系统。
- 当前 `backend/` 只有 SQL 初始化脚本，不代表已经具备可调用的后端 API。接入后端前，前端不得把演示数据表述为线上真实数据。
- 本期交付目标是可演示的“内容展示 + 产品浏览/管理 + 支持资料 + 用户/经销商申请 + 运营后台”闭环；真实支付、退款、物流、库存、ERP/WMS/CRM、多币种与多语言不在本期范围内。
- 不允许直接向 `main` 推送；所有变更都必须通过 Pull Request（PR）合并。
- 每次提交只解决一个明确问题；不要在同一个 PR 混入无关重构、格式化或资源整理。

## 2. 成员分工

成员分工用于明确需求负责人、验收责任和 PR 首要审阅人，不是文件夹所有权。任何成员都可在评审后修改公共目录、修复跨模块缺陷或协助他人；涉及接口、数据结构、路由、公共组件或全局样式时，须在 Issue 或 PR 中说明影响范围。

| 成员 | 负责范围 | 主要验收结果 |
| --- | --- | --- |
| 1 号 | 工程基础与平台能力：应用入口、路由、公共布局、环境配置、后续鉴权接入、数据库演进约定、CI | 项目能启动和构建；公共配置可追溯；跨模块变更有明确说明 |
| 2 号 | 内容展示：首页、品牌/内容页、活动或专题内容、后续内容管理 | 内容页面可访问，文案/图片来源明确，页面适配基础屏幕 |
| 3 号 | 商品与产品画册：分类、列表、详情、规格、后续商品管理 | 商品浏览主流程完整，字段与演示数据一致 |
| 4 号 | 支持中心：FAQ、下载资料、说明书、联系/询盘表单 | 支持入口清晰，表单校验和演示反馈完整 |
| 5 号 | 经销商：申请、审核演示、企业资料、经销商工作台 | 申请至审核的演示流程可走通，Mock 边界标注清楚 |
| 6 号 | 用户中心：登录界面、个人资料、收藏、地址、咨询记录 | 用户侧页面和状态切换可演示；不将 Mock 角色当作真实权限 |
| 7 号 | 运营后台：运营首页、公告、数据汇总、全站基础设置 | 后台演示入口可用；不接管商品、内容、经销商等业务 CRUD |

全组共同负责：主分支集成、回归测试、答辩演示数据检查和课程验收。最终整合不是任何单独成员的模块。

## 3. 代码目录规范

### 3.1 当前基线目录

以下是仓库已合并的目录，所有新功能优先遵循它。不要为了“看起来整齐”批量迁移已有文件，也不要创建 `src/modules/` 作为第二套业务目录。

```text
frontend/
├─ public/
│  ├─ images/                 # 已有静态产品、内容图片；通过 /images/... 访问
│  └─ logo.svg                # 不经 Vite 打包处理的静态文件
├─ src/
│  ├─ App.vue                 # 根组件
│  ├─ main.js                 # Vue、Pinia、路由和 UI 库入口
│  ├─ router/                 # 路由定义；后续路由守卫也放这里
│  ├─ views/                  # 路由页面，如 HomeView、ProductDetail、AdminView
│  ├─ components/             # 两个及以上页面复用的界面组件
│  ├─ stores/                 # Pinia 状态；当前包含 Mock/本地持久化状态
│  ├─ data/                   # 仅演示 Mock 数据或静态页面段落数据
│  └─ styles/                 # 主题变量、全局布局和基础样式
├─ index.html
├─ package.json
└─ vite.config.js

backend/
└─ sql/
   └─ init_schema_and_data.sql # 当前本地演示库初始化脚本；会重建表，仅限开发环境
```

### 3.2 新增代码放置规则

| 内容 | 放置位置 | 规则 |
| --- | --- | --- |
| 新的可独立访问页面 | `frontend/src/views/` | 页面名称使用 `XxxView.vue`；路由同步登记在 `router/` |
| 跨页面复用的 UI | `frontend/src/components/` | 组件名使用 `PascalCase.vue`；不能只因一个页面使用就放入公共目录 |
| 某个页面独有且复杂的子组件 | `frontend/src/views/<页面名>/components/` | 仅在该页面组件达到多个时建立，避免顶层 `components/` 堆积 |
| 前端状态 | `frontend/src/stores/` | 一个领域一个 Store；不要在多个组件直接读写同一份 `localStorage` |
| 演示数据 | `frontend/src/data/` | 文件名须含 `mock` 或在文件头注明“演示数据”；真实接口接入后逐步移除 |
| 后续 HTTP 请求 | `frontend/src/services/` | 接入 API 时创建；页面和组件不能直接散落调用 `axios` 或 `fetch` |
| 通用组合式逻辑 | `frontend/src/composables/` | 以 `useXxx.js` 命名，例如 `usePagination.js` |
| 纯工具函数 | `frontend/src/utils/` | 无 UI、无 Store 状态、可独立测试 |
| 常量和枚举 | `frontend/src/constants/` | 路由名称、状态值等统一定义，避免多处硬编码 |
| 类型定义 | `frontend/src/types/` | 项目采用 TypeScript 后建立；在此之前不为目录而创建空文件 |
| 构建期导入的图片/字体 | `frontend/src/assets/` | 仅放 `import` 使用的资源；原样静态图片继续放 `public/` |

新增 `services/`、`composables/`、`utils/`、`constants/`、`types/` 或 `assets/` 时，按需要创建，禁止先建立空目录占位。

### 3.3 后端与数据库的演进规则

后端服务尚未建立时，不创建空的 `backend/src/` 或伪 API。开始后端开发时采用以下结构，并在对应 PR 中写清前端联调方式：

```text
backend/
├─ src/                       # 后端应用代码；启用后再创建
├─ migrations/                # 可顺序执行、不可删除历史的增量变更
└─ sql/
   ├─ schema.sql              # 空数据库的基础结构
   └─ seed.sql                # 仅答辩/本地开发使用的演示数据
```

- 现有 `init_schema_and_data.sql` 会删除并重建表，只能用于本地演示库，不能用于共享库或生产库。
- 新增字段、索引或表必须使用一份新的增量迁移；不得直接修改已在多人环境使用的历史迁移。
- 数据库变更与依赖它的前端功能可在同一 PR 中提交，但 PR 必须写明执行顺序、回滚方式和演示数据影响。

## 4. 分支与提交规范

模块代号用于说明此次变更范围，不表示某位成员独占该目录。推荐代号：`platform`、`content`、`product`、`support`、`dealer`、`account`、`operation`；也可使用 `web`、`db`、`docs`、`config`、`assets`。

分支格式：

```text
<模块代号>-<姓名拼音>-<简短英文描述>
```

例如：

```text
product-zhangsan-product-detail
dealer-lisi-application-validation
db-wangwu-split-seed-script
```

提交信息与 PR 标题格式：

```text
<模块代号>-<姓名拼音>: <简短中文介绍>
```

例如：

```text
product-zhangsan: 新增商品详情规格展示
dealer-lisi: 修复经销商申请必填校验
db-wangwu: 拆分演示数据初始化脚本
docs-chenyi: 更新团队协作与版本规范
```

一个分支只处理一个功能点或缺陷；PR 合并后删除远端分支，不复用已合并分支继续开发。

## 5. 上传代码流程

```bash
# 1. 开发前同步 main；若本地有未提交修改，先处理或暂存
git switch main
git pull --ff-only origin main

# 2. 从最新 main 创建功能分支
git switch -c product-zhangsan-product-detail

# 3. 开发后检查变更
git status
git diff

# 4. 只暂存本次需要的文件并提交
git add frontend/src/views/ProductDetail.vue
git commit -m "product-zhangsan: 新增商品详情规格展示"

# 5. 推送分支并在 GitHub 创建目标为 main 的 PR
git push -u origin product-zhangsan-product-detail
```

不要执行 `git push origin main`，不要使用强制推送覆盖他人代码。发生冲突时，由 PR 作者同步最新 `main`、在本地解决并重新验证后再推送。

## 6. PR 审核与合并

PR 描述必须包含：

```markdown
## 改动内容
- 页面 / 组件 / 状态 / 数据库 / 文档：

## 验证方式
- 执行命令或手动步骤：
- 验证结果：

## 影响范围
- 涉及目录或模块：
- 是否含 Mock 数据、环境变量、迁移或接口变更：是 / 否

## 截图
- 有页面改动时附截图；无页面改动可写“无”
```

- 合并 `main` 前必须至少取得一位非 PR 作者、且具有写入权限成员的审批。
- 具有管理员权限的成员可在满足审批规则后合并；PR 作者不得自行审批自己的 PR。
- 涉及路由、全局样式、Store、公共组件、数据库结构或未来接口契约时，PR 必须说明兼容性和影响范围。
- 不提交真实密钥、Token、数据库密码、真实用户隐私、`node_modules`、构建产物、日志、本地缓存或未经授权的资源。
- 当前没有自动化 CI 时，提交者至少执行 `npm run build` 或给出同等的手动验证记录；引入测试/CI 后以仓库脚本为准。

## 7. 版本与交付规范

采用语义化版本 `MAJOR.MINOR.PATCH`，课程项目建议从 `v0.1.0` 开始：

| 版本 | 交付内容 |
| --- | --- |
| `v0.1.0` | 当前前端基线、演示数据与数据库初始化脚本可运行 |
| `v0.2.0` | 内容和商品浏览主流程完善 |
| `v0.3.0` | 支持中心、用户中心、经销商申请流程完善 |
| `v0.4.0` | 运营后台、质量检查、全员回归与答辩数据整理 |
| `v1.0.0` | 课程答辩交付版；冻结新功能，只修复阻塞性问题 |

发布 Release 时写明新增功能、修复问题、已知限制、是否仍使用 Mock 数据，以及数据库迁移或环境变量变化。
