# WEMOVE 三天开发 AI 协作约束

本文件适用于本轮 7 个 MVP Issue。每位成员把自己的 Issue 正文和本文件一起提供给 AI；以下规则以简单、可执行为准。

## 统一规则

1. **只做本 Issue**：先阅读 Issue 的目标、验收和“不做项”，不要顺手扩展支付、物流、多语言、微服务等范围。
2. **沿用现有技术栈**：前端使用 Vue 3、Vite、Pinia、Element Plus；后端使用 NestJS、TypeORM、MySQL。未经全组确认不更换框架、不重复引入 UI 库。
3. **必须使用真实数据**：业务状态写入 API 和数据库。`localStorage` 只能保存游客购物车或纯界面偏好，不能模拟登录身份、管理员权限、产品发布、经销商审核或订单成功；真实请求失败时禁止回退 Mock 假装成功。
4. **遵守公共契约**：API 使用 `/api/v1`、JSON camelCase 和统一成功/错误结构；权限由后端判断。公共契约确需修改时，先在 Issue 留言通知受影响成员。
5. **控制修改范围**：后端公共目录由平台负责人维护，前端路由、布局和后台外壳由前端负责人维护，Compose/CI 由交付负责人维护。其他成员优先在自己的领域目录增加模块，避免多人同时重写共享文件。
6. **数据库只做增量迁移**：不要改写已执行迁移，不在应用启动时执行 `DROP TABLE`，不提交密码、密钥或真实个人数据。
7. **完成一条真实闭环**：每个功能至少验证一次“前端操作 -> API -> 数据库 -> 刷新或重启后仍存在”，并覆盖一个失败或无权限场景。
8. **提交前实际验证**：至少运行相关构建、测试或可复现的人工步骤；PR 写明执行命令、结果、截图或响应样例，以及仍未完成的内容。不得伪造测试通过。
9. **小步提交**：每人使用独立分支，建议最多两个主 PR；不直接推送 `main`，不覆盖或回退别人的修改。发生冲突时保留双方工作并请求对应负责人协调。
10. **未实现就关闭入口**：支付、真实订单、库存、报价等未完成能力应隐藏或标注“暂未开放”，禁止用固定成功数据冒充完成。

## 本轮特殊提交约定

- `chenyi-c` 负责站点配置、部署和交付任务的实际开发。
- `chenyi-c` 的分支推送、Issue 关联和 PR 提交统一由 `lizhikeer` 代管；PR 正文同时注明实际开发者与代提交者。
- 代提交不改变实际工作归属，提交记录和课程材料中应如实记录双方角色。

## AI 开始与结束检查

开始前只确认三件事：当前 Issue、允许修改的目录、依赖的 API 字段。结束前只确认三件事：验收项是否满足、真实命令是否运行、未完成项是否写进 PR。
