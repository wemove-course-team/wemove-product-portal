## 性能与可用性目标

选题要求首屏不超过3秒、100并发关键页面响应不超过2秒。课程测量约定如下；P95、数据量和负载比例是本规划为可复现性补充的测试条件，不是教师原文。

| 项目 | 课程目标与测法 | 商业阶段目标 |
| --- | --- | --- |
| 关键API | 100虚拟用户、预热30秒后持续3分钟；请求比例产品列表40%、详情40%、新闻20%；关键请求P95<=2秒、错误率<1% | 常用公开读API P95<500ms |
| 数据集 | 1000产品、100篇新闻、100个合成账户；报告记录CPU/内存/DB/网络、脚本与commit | 依实际规模、冷热缓存分别压测 |
| 页面 | 生产构建，清缓存；首页/列表/详情手机模拟网络连续3次记录首屏时间，目标<=3秒；不得用API耗时冒充页面首屏 | LCP<=2.5s、CLS<=0.1、INP<=200ms，基于实际访问测量 |
| 资源 | 路由懒加载；首屏必要图片压缩、尺寸合理；原图留存 | 响应式格式、CDN和发布缓存失效 |
| 可用性 | Linux服务器Compose部署可复现，连续运行、容器重建与重启后持久化检查 | 月99.9%为目标，部署监控后才报告达成情况 |
| 恢复 | 每日/交付前备份，RPO24h/RTO2h目标，记录一次恢复 | RPO15min/RTO1h目标，定期演练 |

固定压测条件，保存原始输出，不用单次最快值替代P95。现有237MiB静态资源与主包告警为Q02待处理；压缩只处理实际使用资源，不删除原始文件或重写历史。

## 合并与发布门槛

M0使用已存在build；B04补齐轻量lint/必要测试脚本后启用相应检查，新增后端时再加入真实后端构建和接口测试，禁止用echo占位绿灯。数据库验证使用可丢弃测试库，不连接真实共享库。

正式部署须满足 [Docker/Linux基线](deployment.md)：Linux镜像构建与Compose解析通过、db/api/web健康、一次性迁移成功、数据卷重建不丢数据、备份恢复、同源API/HTTPS会话和对外端口检查。实际服务器性能结果才用于最终报告；目前未运行这些检查。

一个非作者审批、已启用CI通过、相关用例有证据、无未处理的阻塞缺陷后方可合并。发布记录commit、环境、迁移版本、执行顺序、已知限制和回滚办法。构建成功不代表浏览器通过，页面503/404或假成功必须明确列出。

课程交付冻结后只修登录失效、数据丢失、关键页面不可用、越权及阻碍演示的UI等问题。商业化前额外完成MFA、私有媒体、资源授权、真实邮件、备份监控和SEO门槛，再决定开放真实用户。
